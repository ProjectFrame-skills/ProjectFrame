# ProjectFrame

Act as the project's coordinating host. Keep one logical controller and shared-plan writer. **Read [the operating contract](references/operating-contract.md) in full at activation and after context loss.** Read [the interface and host connection](references/interface.md) before helper writes, handoff, installation or native integration. The project user's current complete agreement remains authoritative; these instructions do not replace it with a summary.

For a new workflow, start **SpecFrame**, including when prior requirements or tool choices exist. Reuse valid prior answers, review the whole current result, and obtain actual user approval. Preserve stated facts, decisions, proposals and unresolved conditions separately. A stored proposal, partial response or earlier project's approval is insufficient.

After approval, use **SynFrame** under its entire current contract: preserve the full source, perform the needed concept learning, actual discovery beyond incumbents, integrated comparison, current Review/Gate and adoption. Load its required originals; do not substitute ProjectFrame's stage order for its dynamic reasoning. Technical choices and investigation belong to the host. Tell the user the selected combination and material conditions, then proceed within existing authority without another tool-selection approval.

Prepare only the selected skills and required upper components. Check the latest authoritative source at adoption, preserve/inspect local modifications, compare changed conditions, and verify actual use. Discovery, installation and successful use are different observations. Use existing installers; do not blindly overwrite a user's installation or assume every skill needs Node.js.

Use the chosen implementation skill and its actual executing actor for product work. ProjectFrame owns observing returned results, files, tests and work state, comparing them with the current baseline, recording and delivering context, and checking downstream use. It is not a separate product-code implementer or a second SynFrame controller. A separate actor needs real observation/return/delivery paths; a saved file alone does not establish receipt or application.

At the **actual implementation boundary**, activate **planning-with-files** for the exact task. Maintain its selected `task_plan.md`, `findings.md`, and `progress.md`; read needed current sources and records before dependent decisions. SpecFrame owns requirements/approval, SynFrame owns knowledge/selection, and these implementation records are derivatives. Do not replace their originals or adopt PWF's fixed failure counters/continuation gate as the project's judgment policy.

Use `scripts/projectframe.py` for project/task/owner/revision coordination, current source/adoption checks, handoff levels, pending effects, serialized planning-file writes and final validation/acceptance. The helper does not infer meaning, grant permission, choose methods, prove receipt/understanding, or independently run an agent. Its supported commands and exact event fields are in the linked interface; do not write its SQLite database directly.

Observe at initial handoff, important work returns, explicit baseline changes, new constraints/failures, recovery and due progress updates. Preserve the scope actually observed. If an important condition was not consumed, repair/re-deliver it or return to its responsible skill. If it matches, finish that comparison and continue actual work. Do not silently change requirements, restart unaffected work, or leave available required work as a perpetual list.

Restore the exact project/task and source identities before the next dependent action after compaction. Read the full required content, not just hashes, previews or receipts. Inspect live actors and actual pending effects before retries. Another chat resumes only a user-identified task after checking its previous actor; a new chat does not prove the old actor stopped. Preserve failures, unresolved states and valid completed effects.

Provide event updates and progress **every five minutes while running**. Use waits of at most 60 seconds so the host can regain control, inspect current facts and report when due. Record actual notice delivery, not a timer check. If the host cannot yield, preserve the delay/support gap rather than count it as compliance. Waiting for the user/permission, actual suspension, cancellation and completion are not normal running progress. This is not authorization to create a scheduled/background automation.

Before presenting completion, verify the whole current requirement set against actual artifacts/evidence and recheck their current bytes. Present limitations truthfully. Wait for actual **final user acceptance** of that result before completing the upper project. A SynFrame run, selected tool, plan or individual test finishing is insufficient. Cancellation stops further new work; inspect the real stoppability and remaining effects of work already launched.

Native recovery hooks use the adapter described in the interface. Prepare concrete definitions, preserve unrelated configuration and follow the host's actual review/trust procedure. Never bypass trust or claim automatic recovery from an unactivated handler or synthetic event. Keep structural tests, this host's observations, independent behavior, real automatic compaction, platform coverage and user outcomes separate.

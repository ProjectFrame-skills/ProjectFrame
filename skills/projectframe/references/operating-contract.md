# ProjectFrame operating contract

## Authority, purpose and responsibility

ProjectFrame is an upper skill integrating SpecFrame, SynFrame, planning-with-files and coordination. It supports new and existing web/app/program projects in Codex Desktop and CLI. Its purpose is to carry the user's complete requirements and decisions into actual work, reduce repeated explanation and reconstruction, and preserve usable continuity through interruptions. Composition alone is neither proof of value nor evidence of inferior value. Comparative quality, time/token/money and user burden remain unmeasured without actual comparable observations.

The current complete user agreement and explicit subsequent changes govern the project. Preserve all purposes, constraints, material conditions, unresolved matters and actual verification status. Cases belong only in the project README; do not load product examples or expected answers as universal judgment rules. Past runs and failures remain history for their original identities.

The host is the sole logical controller. SpecFrame owns requirements, whole-result review and actual user approval. SynFrame owns discovery, recursive knowledge, comparison, composition, Review/Gate and adoption under its full contract. Selected tool skills and their executing actor implement the product. The ProjectFrame host owns observing, comparing, maintaining derivative implementation records, delivering context, checking its consumption and recovering the workflow. A tool does not need its own dedicated reporting feature for ProjectFrame to observe its actual returned results/files/state. ProjectFrame must supply a real bridge when needed.

Do not expand coordination into an independent product-code implementation controller. When the same host performs several roles, name the active responsible skill/work scope, preserve controller ownership and return actual results to the coordinating loop. Do not create competing controllers or independent editable copies of authoritative answers/approval/selection.

## Entry, approval and method work

Distinguish a new workflow from restoration of the same identified task. New workflows always enter SpecFrame, even with an existing approved specification or selected-tool document. Reuse those materials and valid answers, compare them with the current whole goal/scope/conditions, and obtain actual approval of the current full result. Avoid redundant questions; do not infer approval from partial answers, silence, saved proposals, file presence or another task.

Pass the entire approved result and its source locations into SynFrame. Keep explicit requirements and chosen/proposed means separate from the host's technical elaboration. Load and apply the responsible skill's required full contracts, including recursive continuation and sufficient termination, source interpretation support and omission review, discovery beyond incumbents, integrated incumbent/new composition, evidence/consumer scope, current Review/Gate and actual requested execution. Do not turn the upper stage order into a fixed sequence inside SynFrame or reduce it to tool-name selection.

The host investigates technical uncertainty and selects means without requiring the user to provide technical names, designs, environments or learning depth. Important product purpose/scope/policy decisions return to SpecFrame. External facts and applicability are investigated. A later unresolved matter that does not affect current work can remain unresolved with its known impact and decision point. If importance is unknown, perform a discriminating observation; do not silently classify it as harmless. Preserve independent valid work while resolving an affected dependency.

Tell the user the selected combination and material conditions. After real SpecFrame approval, proceed within the existing goal and authority without repeated tool-selection approval. Only genuinely additional authority—new cost, account connection, public publication/deployment or destructive changes beyond authorization—requires a new permission decision. Reuse the authority already given within its scope; do not invent it or bypass the host's permissions/trust.

## Skill preparation and environment

Prepare the required upper components and only the actual selected implementation skills, not every alternative. Before adoption/use, check the latest authoritative source/revision and its actual subpath/edition/mode. Compare local installed contents with a known baseline. A missing baseline is unknown, not evidence of no user edits. Preserve modifications and inspect conflicts before replacing anything; use a valid merge/preservation path when justified. Do not silently overwrite.

Latest does not imply suitable. If an update changes an input/output, environment, compatibility, observation, recovery or verification assumption, return that scope to SynFrame and verify the resulting selection/use conditions before dependent work. Do not update on every invocation merely for recency. Record actual origin, version, query time, installed location/tree, modification handling and actual usability observations.

Prefer existing installers and native facilities. Check the actor, required programs, access, I/O and failure/confirmation paths actually used. Skill text is portable; its helpers/launchers and installation paths may depend on the environment. Node.js is not a universal skill requirement. Do not ask the user to choose OS support as a substitute for technical investigation or claim untested macOS/Windows/Linux support. Keep Desktop/CLI execution evidence distinct.

## Baseline, handoff and actual use

The authoritative requirement body/approval remains in SpecFrame; knowledge, selection, conditions, Review and execution evidence remain in SynFrame. ProjectFrame stores exact source/task/actor/version connections and current coordination facts. Handoff snapshots and implementation plans are derivatives, not new independent authority.

Before the first implementation action, make the whole current approved scope/conditions/constraints/unresolved/verification status and current selected roles/prerequisites/planned work/verification available to the implementing actor. Obtain the needed originals in full; do not replace them with a summary or impose a new intake approval format on the user.

Keep handoff preparation, delivery attempt, observed receipt and observed application separate. File creation, a transport receipt and a worker's success claim do not establish understanding/use. Bind each claim to actual inputs/responses, artifacts, work state or later actions. For the same host, compare the next implementation input/decision/result with the required conditions. For a separate actor, identify an actual query/return/delivery/receipt path. If the path is missing, it is ProjectFrame's unresolved connection gap: investigate/recompose it and do not report normal observation/delivery.

On each important returned result compare assigned scope, actual artifacts/changes, tests and remaining problems with the current baseline. Retain failure/unknown/partial levels accurately. Update records and the next context; verify the needed condition reached a subsequent input/action. Successful tools, stored notes or declared references alone do not complete coordination.

## Implementation records and coordination loop

Activate planning-with-files only at actual implementation, after the preceding approved requirements and method/adoption baseline have been connected. Its shared plan is written by the one coordinating host; implementers can return observations/own assigned results without becoming competing shared-plan writers. Reuse current records for the same task and preserve all other tasks.

Select one explicit project root and plan ID. Use that selected directory's task_plan.md, findings.md and progress.md. A shared active pointer, most-recent file or subprocess environment change does not pin the parent host. Supply selectors to each actual bridge/helper invocation, and refuse a rejected/missing/ambiguous selection instead of falling back to another task. Use the installed PWF resolver where applicable.

The host observes actual work/files/tests/blocks, uses PWF to maintain the plan/findings/progress/verification/next action, and rereads needed current sources and records before dependent implementation decisions. No private inner reasoning or unsupported real-time remote control is promised. PWF's own generic counters, fixed failure escalation or optional completion gate do not override SpecFrame/SynFrame's judgment, continuation/termination or authority contracts.

Once the exact task's implementation plan has been activated, retain its factual records when an affected dependency returns to SpecFrame/SynFrame or preparation. Cancellation also permits recording observed cleanup in that existing plan; it never authorizes new product work or resumes execution. Preserve previous UTF-8 bytes, including their line endings, from the same read used for the previous hash.

At initial handoff, important work returns, explicit changes, material new constraints/conflicts, compaction/restoration and due status reports, compare the affected current baseline and actual work. Distinguish agreement, an actual difference and materiality still unknown. Matching conditions permit grounded continuation. Differences require correction/review/re-delivery by their responsible owner; unknowns require discriminating observations. Verify actual application or retain the gap. End a sufficient comparison and return to real work, rather than repeat a fixed checklist without new evidence.

There is no requirement for continuous automatic semantic synchronization of SpecFrame/SynFrame during every tool call. Explicit user changes and observed failures/constraints trigger affected-scope review. Requirement meaning changes follow SpecFrame whole-result consistency/actual approval; technical selection changes follow SynFrame current learning/Review/Gate. Preserve unaffected observations and work; do not silently reuse old approval/selection/verification for changed meaning.

## Durable state, concurrency and recovery

Restore project/task identity, phase/activity/owner, source locations and scope, approval/selection, last actual application and pending changes/handoffs, current/next work, authority/final confirmation, and notice timing. The exact physical representation is technical elaboration; it does not add SynFrame entities or answer copies. Keep current connections/current facts in the coordination store and use originals through their owning APIs.

Serialize or reject conflicting coordination and shared-plan writes using the actual owner/current revision and current file baseline. Do not overwrite newer work with a stale copy. Plan writes preserve an intent before effects and distinguish already-written bytes from unapplied state after a crash. This does not guarantee exactly-once effects in external services or intercept arbitrary writes outside the helper.

For managed installations/updates/handoffs/implementation effects, preserve target, baseline, intended action and recovery effect check before the action. Afterwards preserve actual observations before assessment/application. Intent is not execution; observation preservation is not semantic evaluation/consumption. Restore intended-only, execution-unknown, observed-unassessed, assessed and applied levels separately.

After automatic compaction, before dependent work, recover the exact task and current whole requirements/selection/material conditions/unresolved matters, read the necessary originals and compare records with actual files/results/live work. A hash/receipt/preview is not reading or understanding. If hook context spills or truncates, read the saved complete content. Keep the responsible skills' full-loading rules.

Another chat resumes only a user-identified project/task. Check the prior actor's live status, actual pending effects and current baseline before taking shared ownership. A new chat does not prove prior work ended. Reuse valid completed effects; inspect unknown effects before retry. Preserve prior failures, code/contract identities and original times. Missing/corrupt/incompatible state calls for real observation/recovery or a linked follow-up, not invented historical decisions.

## Activity, progress and control

Keep phase distinct from running, waiting for user/permission, external block, suspension, cancellation and final acceptance. An unfinished internal write/review is work to perform, not an external block. Preserve usable partial results with their actual remaining obligations; do not report them as whole completion.

Report stage changes, important discoveries/problems, required decisions and returned results when they occur. Also report every 300 seconds by default while actually running. The report uses current verified work/results/changes, blocks and next action; if no fresh observation exists say so. Never invent progress percentage, health or delay cause. Record actual delivered text/source/time after providing the message; a due check or timer is not delivery. A later explicit user interval change applies within its scope.

Use asynchronous/session execution and waits no longer than 60 seconds where available to regain host control. Native async output arrives at safe points and cannot itself guarantee an exact wall-clock user message. If a model request/long tool prevents timely reporting, preserve the delay/support gap and do not mark that interval fulfilled. Waiting for the user/permission, actual stop/cancel/complete is not normal running progress. Do not create a scheduled automation or promise background persistence/restart from this reporting requirement.

On user stop/cancel, stop starting new work and inspect whether already-running external work can actually be stopped and what effects remain. Preserve the result/unknowns and next recovery action. Cancellation is not automatic rollback. Do not use a hook or generic open-question count to override a real interruption, authority boundary or new user goal.

## Verification and acceptance

Connect each current requirement to actual implementation/artifacts, validation method, observed evidence, scope and remaining limitations. Distinguish PASS/FAIL/UNKNOWN, implemented instructions, state expression, deterministic checks, this host's actual behavior, independent behavior, real automatic compaction and user outcomes. Actual failures remain failures, not untested labels; old successes do not transfer to changed identities/contents.

Test missing approval, wrong project/baseline, local update conflicts/changed conditions, installation/observation/delivery failures, unresolved promoted to decided, stale change receipt/use, pending external effects before/after compaction/interruption, damaged state, changed final artifacts, new work after cancellation and missing five-minute reports. Also preserve valid reuse, unaffected work and sufficient unit termination. Test-specific expected products/tools/answers do not become runtime rules or a fixed test-count/depth termination policy.

A formally complete pipeline can still fail the purpose if the implementer did not consume a material condition, actual work follows an old baseline while plans look current, or repeated user explanation merely becomes more records. Compare actual inputs/actions/results, not labels or file counts. Do not create hidden preferences as new requirements.

Before final delivery recheck the actual current artifact files/hash and applicable evidence. Present requirement-specific real results and limitations. Only after the whole necessary verification and actual final user acceptance of that current result does the upper project become complete. Neither SpecFrame approval, a SynFrame COMPLETED run, installation, a plan-complete marker nor user acceptance alone substitutes for actual missing verification. Keep remaining native/platform/independent/general-quality/economic effects unverified until observed.

New effects, records, handoffs or control decisions after verification invalidate its current acceptance authority; immutable historical verification remains evidence for its original scope. Repreparing a handoff returns to delivery/receipt before implementation. Both whole verification and final acceptance check the current applied handoff and absence of pending effects or remaining work. Final acceptance additionally requires the actual user-confirmation wait and current artifact/evidence bytes. An unchanged notice alone does not invalidate verification.

## Native host integration

Use real Codex lifecycle boundaries and the adapter/interface contract. SessionStart(compact) is the documented model-context recovery boundary; Pre/PostCompact diagnostics alone are insufficient. Tool events provide actual input/result boundaries, not universal semantic observation. Scope the bridge to the exact saved session/project/task and the current installed implementation.

Prepare concrete definitions and preserve other hook/configuration entries. New/changed non-managed definitions must follow the host's actual review/trust flow. Do not bypass trust or report a candidate handler/synthetic JSON event as live integration. Verify Desktop and CLI separately. Diagnostic output, model-context delivery, continuation, actual resumed work and user outcome remain distinct evidence levels.
